nTop API Use Case: Custom JSON Output

nTop > Falcon Aero

An AI agent used the prototype Notebook API to add a flight-dynamics export to a hand-built nTop model. The model now measures its own geometry and writes the JSON that Falcon's controllers read. This report explains the method, shows the evidence, and lists the API issues found on the way.

30 AUG 2026AUTHOR: CLAUDE (AGENT), FOR BRAD ROTHENBERGBUILD: NTOP 6.0.0-RC 42594STATUS: WORKING · DENSITY PENDING

Summary

The Notebook API is ready for real work. An agent added 88 blocks to a hand-built airplane model, fully autonomously, and the model now regenerates its Falcon input deck within seconds of any design change.

Every step was verified against the model itself, not against the code that wrote it. The strongest check: the notebook measured the wing's dihedral as 3.0000000000000004 degrees from raw tip geometry, and 3.0 degrees is the design input two custom blocks upstream. The API also has sharp edges. Section 08 lists eleven of them for Anthony, each with the verbatim error message and a workaround.

01What this is about

Falcon builds stability-and-control (S&C) software: the code that decides how an aircraft's control surfaces move. Their tool takes one JSON file, called a deck, that describes the aircraft: where each part sits, how much it weighs, and the shape of each wing. Someone normally types that file by hand from CAD measurements.

The goal of this session: make an existing nTop airplane model produce that file itself, so the deck can never drift out of sync with the geometry. Change the wing, and the numbers Falcon sees change with it.

The tool for the job is the Notebook API, an unreleased prototype. It is a Python object named notebook that lives inside nTop's Python Console and can add blocks, wire them together, and read their properties: the same actions a person performs by clicking in the GUI. It exists only inside the GUI. There is no headless or network version.

02The starting point

Three things existed before the session started, all provided by Brad:

  • The model. Fuse-Wing_R1, a hand-built airplane, open in a development build of nTop. Three implicit bodies: a blended fuselage, a swept two-panel wing, and twin canted fins. It was built for design work, with no export of any kind.
  • The harness. A small repo (Notebook API Demos) with a PowerShell script that types commands into the Python Console and an agent.py module that writes results to JSON files an agent can read.
  • The target. The ntop-falcon repo, which holds Falcon's reference deck (the only specification of the format that exists), a Python package that assembles and validates decks, and a reader that expects one flat JSON of measurements with keys like main_wing__semispan.

Brad made three scoping decisions up front: report the engine and battery from config values since the CAD does not contain them, use one placeholder density for all three bodies, and export raw nTop coordinates with the axis flip handled on the Falcon side.

03How an agent drives a GUI-only API

The API has no socket and no command line. Its one entry point is a text prompt inside a GUI window. The harness turns that into something an agent can operate alone:

  1. The agent writes or edits a Python module on disk.
  2. A PowerShell script finds the Python Console window through Windows UI Automation and types one fixed line into it. That line executes the module.
  3. The module runs inside nTop and writes its results to JSON files.
  4. The agent reads the files, takes a screenshot of the nTop window, and iterates.

The screenshot matters as much as the files. The files say what got wired; the screenshot says what the model looks like. The two channels were cross-checked and agree. Every claim in this report was verified through at least one of them.

04Measure before build

The API is a prototype with no documentation, so the session started by probing it rather than trusting it. A throwaway module (probe.py) added blocks to a scratch section, tried each operation, and recorded what actually happened. Three findings shaped the whole design:

QuestionResultConsequence
Which input types can set_block_input write? real, vector, point only Text and file-path values cannot be authored through the API at all. The export needs 57 text keys and one output path.
Does import_recipe replace the notebook or add to it? It merges Measured with a one-variable test recipe: every section, variable, and custom block survived, and the new variable appeared. This is the escape hatch for the finding above.
Can one call follow a nested property path, such as bounding box.min point? No Each property hop needs its own variable block. This is why the build is 88 blocks rather than about 30.

The probe results drove a two-channel design. A small recipe file carries only the literals the API refuses to set: the 57 key names, the output path, and unit-carrying constants. The agent imports it, then builds everything numeric with the plain API and wires the imported variables in. Nothing is guessed; block identifiers came from the API's own catalog of 2,571 entries.

05What got built

One new section, FALCON EXPORT, added to the model. It contains 88 blocks. One is a temporary list container that the build script deletes after use. The rest form three measurement chains and one output chain:

  • Per body (fuselage, wing, fins): a mass-properties block, its center of gravity, its bounding box, and the box's corner points, each unpacked into plain numbers.
  • Per wing: tip chord and tip position read off the existing tip line, then semispan and dihedral computed from them with math blocks.
  • Output: a dictionary block pairs the 57 key names with the 57 values, a JSON block serializes it, and an export_json block writes the file. nTop re-evaluates the chain whenever an upstream input changes, so the file rewrites itself.

Every block the agent makes carries an FX prefix. That is how the companion reset function finds its own work and removes it without touching the airplane. The build refuses to run twice, because nTop renames duplicate blocks and a second graph would wire to nothing, silently.

06Verification

A build that does not raise an error proves nothing here, because this API's most common failure is a silently unwired input. Four independent checks were run instead:

3.0000000000000004
measured wing dihedral, deg. The design input is 3.0, two custom blocks upstream.
9.144 m
measured fuselage length. Reproduces the LOA_1 design input exactly.
57 / 57
keys paired with values in the right order, confirmed in the exported recipe.
bit-for-bit
export reproduced after a design change was made and reverted.
  • The recipe check. The notebook was exported as recipe JSON and inspected key by key. The dictionary holds 57 text keys and 57 value references, paired positionally, in the order the spec defines.
  • The dihedral check. The notebook does not echo the 3.0-degree design input. It measures the tip line and computes the angle from raw coordinates. Landing on 3.0000000000000004 is independent evidence the chain is wired the right way round. The first build produced 177 degrees, because the wing generator lays its tip out at negative y and the formula lacked a magnitude. The agent caught this by comparing measured output against a known input, and fixed it.
  • The round-trip check. The wing root chord was changed through the API. The export file rewrote itself within seconds with the new planform. Restoring the chord reproduced every one of the 57 numbers bit for bit.
  • The consumer check. The Falcon-side generator read the export, built the deck (Sref 305.787 ft², Cref 12.304 ft, Bref 28.978 ft), and passed its own validator plus 90 unit tests, 28 of them written for this airplane.
Do not trust these masses yet

The model carries no material, so the notebook uses a placeholder density of 1 kg/m³, chosen so mass equals volume numerically and cannot pass for a measurement. Measured solid volumes: fuselage 10.401 m³, wing 4.204 m³, fins 0.335 m³. The engine and battery numbers are hand-entered placeholders in the config, flagged as such, and the deck generator prints a NOT MEASURED warning naming them on every run. Set a real density in the notebook and the whole deck follows.

07The part that was grunt work: reaching the API at all

Most of the session's debugging time went into the transport, not the modeling. The console is a GUI text widget, so commands reach it through simulated keystrokes, and three separate failure modes had to be found and engineered out:

  • The Windows clipboard wedged mid-session. The original script pasted commands through the clipboard. Partway through the day, every Set-Clipboard call began failing with "Requested Clipboard operation did not succeed", no process reported as owner, and it never recovered. The script now stages each command in a file and types only a fixed exec(open(...).read()) line, so nothing variable touches the clipboard or needs keystroke escaping.
  • Simulated typing drops leading characters. Seen repeatedly as a prompt line missing exactly its first nine characters, which then ran as a syntax error while the real command never ran at all. Longer waits did not fix it. The script now reads the prompt line back and retypes until it matches, and only then presses Enter.
  • The console buffer scrolls. Completion was detected by watching the buffer grow. On a long session the buffer hits its size limit and stops growing, so finished commands were reported as timeouts. Completion is now signalled by a marker file the command writes on exit, which also carries the traceback when the command raised.
py> ('D:/...console_cmd.py').read())
  File "<stdin>", line 1
    ('D:/...console_cmd.py').read())
                                   ^
SyntaxError: unmatched ')'

The transcript above shows failure mode two as the console saw it: the launch line arrived without its first nine characters. None of this is a Notebook API defect. It is the cost of the API having no entry point other than a GUI widget, which is why Section 08 ends with a transport suggestion.

08API findings, for Anthony

Everything below was measured on build 42594, most of it with error text captured verbatim. Severity reflects the agent's experience: Blocker stopped work until a workaround existed, Trap produces wrong results or dead ends silently or confusingly, Note is behavior to document rather than change. Numbering follows the order of discovery, so the most consequential finding is last.

#SeverityFindingWorkaround used
1Blocker set_block_input accepts only real, vector, point. Verbatim: "Parameter "0" of block "Text List_0" has type "text", which cannot be set yet". Same refusal for file_path, real_field, integer, bool. A text literal or an output path cannot be authored at all. Carry such literals in a recipe fragment and import_recipe it, which merges. Works, but is a second authoring channel with its own value encoding.
2Blocker set_block_input and get_block_input speak the notebook's display units, not SI. Reading a 5.4864 m chord returned 216.0 (inches). Setting 6.0 sets six inches. The recipe format stores SI. Mixing the two rescales a model by 39.37 with no error. Read every value back after setting it, and keep unit-carrying constants in the recipe channel. An API-level fix: accept and return SI, or expose the display unit.
3Trap add_variable wraps an ordinary block in a new core.var instead of renaming it. Wiring into the returned id then fails: "Block "FX fuselage Mass Properties" has no parameter named "Body"". Worse, the inner block becomes unreachable by set_block_input ("No block with the id "Mass properties_0" exists") while connect_block_property still resolves that same id. Two functions, two id scopes. Set every literal input before naming the block, keep both ids, wire inputs to the inner one. The reply's funcId reveals whether a wrap or a rename happened.
4Trap Reusing a plain block's output in two places silently drops all but one connection. No error is raised. This is the API's most dangerous behavior, because the model looks complete and computes with missing inputs. The moment an output feeds two inputs, make it a variable and reference the variable everywhere.
5Trap Property paths are one level deep. "Block "Fuse" has no property named "bounding box.min point"". A slash separator fails the same way. One core.var block per hop. Roughly triples the block count of a measurement chain.
6Trap append_to_list cannot fill an empty list input on some blocks: "Input "Values" of block "Dictionary_0" holds no list to append to". Yet boolean_union's Bodies input self-seeds from bare appends. The rule is per-block and undiscoverable except by trying. Seed slot 0 through a core.list container, connect it, append the rest, then delete the container nTop leaves orphaned after inlining.
7Trap import_recipe merges block content but overwrites the notebook's display name and description. Importing a literals recipe renamed Fuse-Wing_R1 in the tree header. The literals recipe now carries the host notebook's own title back.
8Trap A fresh core.var arrives with its Input already holding a default value, and connect_block_property refuses to replace it: "Parameter "Input" … already has a value, which this call does not replace". Call clear_block_input first, but only after the plain connect fails, so genuine wiring mistakes still raise.
9Note Cleanup is asymmetric. delete_block refuses variables, deletion order matters, there is no delete_section, and each delete re-evaluates the notebook, so removing 88 blocks takes minutes. The empty FALCON SCRATCH section in Figure 3 is permanent. Prefix everything, delete in reverse creation order, run a second pass for blocks freed by the first.
10Note The API exists only as an object inside the GUI console. Everything in Section 07: UI Automation, keystroke loss, clipboard failure, buffer scraping, exists solely to reach it. A local socket, named pipe, or stdin channel into the console would remove that entire layer and make the API usable from CI.
11Blocker The API cannot make a notebook automatable. There is no add_input, no promote_to_input and no set_output, so a notebook authored entirely through this API has nothing for ntopcl -j to set and nothing for -o to return. Measured on the finished model: ntopcl -t returns "inputs": [] and fails with "Error generating output template : Output of function not set", exit code 1, and -o writes no file. Every design variable here is a core.var<real> the API can set and ntopcl cannot reach. Export blocks fire headless even with no output set, so a notebook can report by writing its own file, verified: ntopcl built the chain, ran the export and exited 0. That covers one run, not a sweep, because the path is a fixed literal. The recipe format carries inputs and output at the top level; whether import_recipe honors them is untested.
The one to fix first

Findings 1 through 10 cost an agent time. Finding 11 caps what the API can produce: it authors models that only a person can drive. promote_to_input(block_id, name, description) and set_output(block_id) would together turn an API-authored notebook into something ntopcl can sweep, which is the difference between authoring a model and shipping a pipeline.

Reproduction

Every finding above reproduces from nTopScripts/probe.py in the harness repo: probe.setters, probe.wiring, and probe.import_probe re-measure findings 1, 2, 5, 6, and 8 in about a minute. Re-running them after a build bump is much cheaper than rediscovering the traps.

09Why this is a good test case for the API

This task is exactly the work nobody wants to do by hand. Building the export section means placing 88 blocks, making roughly 200 wiring calls (est.), and keeping 57 keys paired with 57 values by position, where a single swap corrupts the deck without any error. It is precise, repetitive, and unforgiving: grunt work.

The agent did it in about 75 minutes of wall clock (derived from file timestamps), including three failed builds, the dihedral bug, and a rewrite of the console transport. What made that possible was not speed. It was that the API let the agent close its own loop: build a piece, export the recipe, read back what actually got wired, screenshot the model, and correct. The 177-degree dihedral was caught because a measured output disagreed with a known input, which is the same discipline a good engineer applies, executed automatically.

The result is a pattern, not a one-off. Any notebook can be given a self-updating measurement export with the same recipe-plus-API technique, and the harness, probes, and traps are documented in the repo for the next agent or the next person.

The pattern stops one step short of a DOE sweep, and finding 11 is why. The measurement chain itself is sweep-ready: ntopcl re-evaluates it headless and rewrites the file, verified. What is missing is that the model exposes no inputs for a sweep to vary and no output for it to collect, and the API cannot add either. Until that is fixed, making a model sweepable needs a person in the GUI, whatever else the agent did on its own.
