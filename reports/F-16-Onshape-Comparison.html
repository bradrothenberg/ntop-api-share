01Executive assessment

This study asks where each tool helped an agent create, change, and verify an aircraft model. It compares the delivered independent Onshape model with the retained nTop revision 3 model. It is a build case study, not a controlled product benchmark.

nTop delivered the stronger current aircraft shape. Onshape provided a clear component-based CAD model with editable feature dialogs and a shared browser document. The main nTop advantage was the composition of smooth geometry with fields. The main Onshape advantage was the organization of conventional CAD parts and parameters. These conclusions apply to this implementation and workflow.

For a refined outer shape with spatially varying geometry, this build favors nTop. For component editing and browser-based review, the Onshape model offers a useful alternative. Neither result establishes a winner for engineering time, cost, flight performance, or manufacturing readiness.

The competitive implication for nTop is direct: programmable parametric geometry is available in both tools. nTop must show the value of its field representation, reusable geometry methods, and automated validation. The presence of code generation alone does not distinguish it.

All measurements below are internal results from retained build records. Product capabilities are identified as documented when they were not tested. Recommendations are inferences from this case.

03What the builds were like

Onshape work centered on CAD operations and application state. The agent defined section profiles, lofted components, managed body queries, and exposed parameters through FeatureScript. The resulting feature tree provides a short route to wing, fuselage, canopy, inlet, and tail controls.

The main corrections involved FeatureScript rules, feature ordering, and geometric reconstruction. Reserved identifiers caused compile errors. A property query could not run during regeneration. Tracking component queries explicitly resolved that diagnostic issue. A contact audit found that tail roots obstructed the duct because the cut occurred too early. Moving the cut to the final feature fixed the obstruction. These were implementation mistakes, not demonstrated kernel defects. Independent build specification and record, FeatureScript source.

The browser added separate friction. Sign-in required the user. Some displayed results lagged regeneration, so the agent had to confirm that the current model had finished. The successful export used an STL stored in a document tab, followed by a refresh and download. This experience describes the integration used for the task; it does not measure Onshape's geometry-engine speed. Onshape build record, retained native output.

nTop work centered on field construction and numerical inspection. The agent built native spline guides, conic fields, a cubic Bezier field, airfoil thickness functions, and smooth component unions. A generated recipe encoded block signatures and connections. ntopCL converted that recipe into a native notebook and evaluated it. This F-16 build did not use the Python Console Notebook API. Recipe writer, native runner.

The main corrections involved guide coordinates, signed-field behavior, and preview bounds. Small field probes helped verify inside/outside conventions before the full build. Thin tails and wings looked jagged when preview bounds were too large. Tighter bounds and higher display resolution improved inspection. That preview issue must be separated from the underlying implicit geometry. The third revision replaced projection-based outline construction with smooth native geometry. Spline study, nTop design specification.

04Where Onshape has the advantage

Component controls are easy to locate

The delivered Onshape tree groups the model into named features. Double-clicking a feature opens its controls. A wing sweep change from 40° to 45° moved the aft bounds of both wings by 0.784679 m. Fuselage, canopy, and vertical-tail bounds stayed unchanged. That is direct evidence of a useful component editing workflow. Native control verification.

This organization may reduce the effort needed for another CAD user to find a parameter. That usability benefit is an inference, not a measured user-study result. nTop also exposes model controls. Further Onshape edits beyond the supplied parameters require work in the custom feature source; the short tree does not expose every construction detail.

Native parts support conventional CAD work

Onshape produced distinct solids with faces and edges. This is a useful starting point for subsequent interface, part, and assembly work. The benefit follows from the delivered representation, but those downstream tasks were not tested here. The present overlapping airframe still needs additional construction work before a manufacturing handoff.

The document is directly accessible in a browser

The agent and user used a shared Onshape document during the task. Reviewers with permission can open the same Part Studio. Onshape also documents simultaneous editing, comments, access control, and version workflows. Those broader collaboration capabilities were not tested in this study. Onshape collaboration.

Custom-feature automation is a credible competitor

FeatureScript let the agent package geometry and parameters into reusable native CAD features. Onshape documents this workflow as configurable, parametric feature authoring. The build therefore demonstrates more than an imported mesh or a static CAD translation. Onshape custom features.

Onshape also offers an official FeatureScript MCP server through Onshape Labs. Its documentation describes writing FeatureScript into documents, inspecting errors and geometry, and iterating from an assistant. It was not connected or tested for this build. It could reduce the browser friction we encountered, but that benefit still needs measurement. Onshape FeatureScript MCP.

05Where nTop has the advantage

Smooth geometry composition worked well in the delivered model

The nTop airframe combines separate components through smooth unions. Spline and conic fields control the fuselage, while guide curves control thickness, chord, datum, and twist. The retained model shows more developed wing and tail attachments than the Onshape result. These joins were defined through field operations, without selecting individual B-rep edges for fillets. Native graph checks, spline study.

This is the strongest observed nTop advantage in the study. It does not show that Onshape cannot create smooth blends or that all nTop changes will regenerate correctly. The Onshape reconstruction stopped at a less refined state.

Continuous spatial controls fit the modeling problem

The nTop construction expresses shape through continuous functions and guide fields. These can change geometry across a region instead of only changing one global dimension. The F-16 uses this approach for its outer shape and attachments.

nTop documents a broader field-driven workflow in which geometry, measurements, or simulation results can control spatial design parameters. That capability could matter for graded structures or simulation-driven geometry. This aircraft study did not build a lattice, map simulation data, or demonstrate a performance improvement. nTop field-driven design.

Native numerical checks and headless execution supported iteration

The retained nTop tests sample the implicit field at selected points. They check airfoil thickness locations, component interiors, and duct clearance at specified stations. The same test process ran at 32 ft, at 32 in, and after reset. That is useful evidence for automated geometry checks. Smooth delivery checks, scale checks.

The build also exercised command-line conversion and evaluation. nTop Automate documents headless notebook execution on desktops, servers, and cloud systems. This supports repeatable parameter studies without a modeling window. The F-16 recipe authoring route used specific native block signatures and a retained build; its portability was not established. nTop Automate, native runner.

The current nTop shape matches the retained drawing more closely

This is a delivered-model result, not a platform accuracy ranking. Onshape used an F-16C reference. nTop was refined against the F-16A drawing used for scoring. The span conventions differ, and fixed registration can amplify vertical datum differences in the front view. These factors prevent a controlled comparison of platform capability.

The Onshape model also lacks continuous root blends and tip rails. Its nose, wing placement, and tail placement differ from the retained drawing. Those visible construction differences require more work regardless of the precise score. The nTop wing uses a symmetric NACA-family thickness law with a finite edge allowance; Onshape uses cambered NACA 64A204 coordinates. That airfoil choice is an implementation difference, not a limitation of either tool. Onshape source choices, nTop specification.

07Competitive implications for nTop

The following priorities are inferences from one agent-assisted case. They need broader user and workflow validation before becoming product commitments.

The case supports evaluating a workflow that uses conventional CAD for part interfaces and nTop for field-driven geometry. That combined workflow was not exercised here. It should be assessed through an actual handoff, with measured losses and edit behavior.

08A fair next comparison

  1. Use one geometry specification. Fix the aircraft variant, source drawing, airfoil, span convention, datum, and required component list. Define which dimensions are source measurements and which are design choices.
  2. Require the same completion criteria. Specify root continuity, duct clearance, parameter ranges, separate-part outputs, and any required fused or manifold deliverable.
  3. Compare supported agent integrations. Test Onshape's FeatureScript MCP and a documented nTop automation route. Record setup time separately from repeated modeling work.
  4. Measure matched operations. Log active authoring time, unsuccessful iterations, native regeneration, inspection, and export. Run the same dimensional and component-shape changes in both tools.
  5. Evaluate geometry and handoff independently. Compare registered silhouettes, available three-dimensional references, minimum clearances, and exported topology. Record failures across parameter changes instead of relying only on a successful baseline.

The next benchmark should determine how much effort each tool needs to reach the same acceptance criteria. This report does not provide an estimated duration or expected winner for that experiment.

09Sources and confidence

High confidence: model representation, retained parameter results, exported Onshape mesh measurements, source independence, and recorded silhouette scores. These are supported by local artifacts and scripts.

Qualified confidence: relative ease of editing, workflow friction, and the proposed product priorities. These observations come from one agent-assisted implementation with unequal refinement and integration.

Not established: comparative engineering speed, total cost, general robustness across design space, manufacturing readiness, structural performance, or flight performance.
