# Engineering Report

Build a reviewer-ready PDF report where every figure is generated by a
script (never a hand-taken screenshot), every claim is backed by a number
you measured, and the whole thing regenerates in minutes when the data
changes.

For HTML output, use [engineering-html](../engineering-html/SKILL.md).
The rendering references retain recorded recipes; recheck them against the current data and software.

## Why scripted figures

Reports get regenerated: the mesh changes, the run converges further, a
reviewer asks for one more view. If figures come from scripts with locked
cameras, regeneration is a re-run; if they come from interactive
screenshots, it is an afternoon. Scripted figures are also the only way to
guarantee that "before vs after" pairs are actually comparable.

## Workflow

1. **Collect the numbers first.** Tables carry the report. Gather the
   quantitative results (element counts, projection percentages, error
   norms, timings, pass/fail gates) before writing anything. If a number
   the narrative needs doesn't exist yet, measure it - do not estimate.
2. **Plan the figure list.** Aim for 3-6 figures that each earn their
   place: one overview/context shot, close-ups where the phenomenon
   lives, and comparison pairs for any before/after claim. Sketch the
   list with a one-line caption each BEFORE rendering; if you can't write
   the caption, the figure isn't needed.
3. **Probe, then finalize.** Render a cheap probe of each view, Read the
   image back, and fix cameras/ranges/clims before the final
   high-resolution pass. Never ship a figure you haven't looked at.
   - Mesh figures, pyvista route (PREFERRED for publication look:
     smooth-shaded curved surfaces, per-actor composition, no GUI
     flash): read `references/pyvista_ho_meshes.md` - true order-3
     rendering of gmsh tri10/prism40 elements (Lagrange triangles,
     empirically-derived prism node table + Vandermonde face
     tessellation) and the wireframe gotchas (PolyData auto-verts,
     line depth offset, hairline-via-oversampling).
   - Mesh figures, gmsh batch route (whole-mesh clip-plane volume cuts,
     zero scripting): read `references/gmsh_screenshots.md` - camera
     math, clipping recipes, high-order element handling, and several
     crash/artifact gotchas that cost hours to discover.
   - Flow/field figures (VTU + pyvista) and profile plots (matplotlib):
     read `references/flow_fields.md`.
4. **Crop comparison pairs identically.** Both images of a pair must use
   the identical camera AND the identical crop box (union of content
   bounding boxes) or the comparison silently breaks. Use
   `scripts/crop_pairs.py`.
5. **Assemble with reportlab** using `scripts/report_style.py` (house
   styles, tables, figure-pair helpers). Structure below. Run with
   `uv run --with reportlab --with pillow --with fonttools python make_report.py`.
6. **Verify the PDF.** Render every page back to PNG with
   `scripts/verify_pdf.py` and Read the key pages. Check: figures show
   what captions claim, tables fit, no orphaned captions. Fix and
   rebuild until clean.
7. **Deliver next to the data.** Write the PDF into the project's output
   folder (not a temp dir), copy the final figure PNGs into a
   `report_figures/` subfolder beside it (users reuse them in slides),
   and keep the generation scripts so the report is reproducible.

## nTop report design

Follow the local `ntop-design-v1` and `ntop-docs-v1` design tokens.
Use the values below when those skills are unavailable.
The user prefers blue report highlights, which overrides the source skills' orange document accent.

- Highlight text, links, section numbers, key values, and callout labels use nTop blue `#16489D`.
  Use `#248AFF` on dark backgrounds. Keep ordinary bold text in the body text color.
  Use `NT.accent` and `highlight("selected words")` from `scripts/report_style.py`.
  The helper escapes plain text and returns blue inline markup for a ReportLab Paragraph.
- Use a cool grey page `#F7F8FA`, white surfaces `#FFFFFF`, and panel grey `#F0F2F5`.
  Use ink `#262626`, headline ink `#0A0A0A`, muted text `#6D6C6A`, and rules `#E4E7EC` / `#CBD0D8`.
  Use the pale blue tint `#EDF2FB` for callouts with a blue left rule.
- Prefer Aeonik for headings and body when a licensed local font is available.
  The PDF helper selects local Aeonik when available, then IBM Plex Sans, then Helvetica.
  Use Aeonik Fono when available, then IBM Plex Mono, for labels, table headers, metadata, and code.
  Use a sans-serif heading family. Apply a condensed heading style only when requested.
- Use a clear title, a short purpose statement, mono metadata, and numbered evidence sections.
  Keep generous whitespace and thin section rules.
  Use mono uppercase table headers on grey panels, white rows, and horizontal rules.
- Use one blue highlight per visual group. Use neutral colors for supporting chart series.
  Preserve meaningful scientific color scales and labeled pass/fail colors.
- Keep the engineering structure below. Apply the deck's blue emphasis to the document layout.

Use `build(doc, story)` from the helper to apply the page background and running footer.
Inspect the rendered PDF to confirm the exact blue, clear hierarchy, and readable tables.

## Local Aeonik fonts

For licensed Aeonik typography, place `aeonikvf.ttf`, `aeonikvf-italic.ttf`, and
`aeonikfonovf.ttf` in the skill's private `assets/fonts/` folder, or point
`NTOP_REPORT_FONT_DIR` to a private folder containing these files.
Run the report builder with `uv run --with reportlab --with pillow --with fonttools python make_report.py`.
The helper selects Aeonik Regular, SemiBold, Bold, and italic weights for the PDF.
It uses Aeonik Fono for labels and code. FontTools selects each variable-font weight in memory;
the source files stay unchanged, and the PDF embeds the used glyphs.
Without these files or FontTools, the helper uses its IBM Plex or standard PDF font fallbacks.

The supplied CoType desktop license permits PDF embedding and prohibits transfer of the font files
to third parties. Keep the font binaries local. The public skill excludes `assets/fonts/` from Git.

## Report structure

Follow this skeleton unless the user asks otherwise:

- **Title block** - specific title, author, date. If results are still
  being produced, subtitle "interim report; X in progress" - never imply
  completed work that isn't.
- **Abstract** - one paragraph with the headline numbers in it (the
  reader should get the whole story here: what was done, the key
  quantities, the one caveat that matters).
- **Numbered sections** - typically: setup/pipeline (with the exact
  commands used, in monospace), quantitative results (styled table with
  caption), figures section, conclusions + next steps.
- **Figure pairs** - side by side with "(a) <baseline>" / "(b) <new>"
  sublabels and a caption that states what to look at and what it
  demonstrates.
- **Honest captions and caveats** - if a figure contains a rendering
  artifact, say so in the caption and state why it is not a data defect
  (reviewers WILL ask). If a result is preliminary, unsteady, or has a
  known limitation, put it in the text - a report that hides a weakness
  gets less trust, not more.

## Writing style: ASD-STE100 (Simplified Technical English)

Write all report prose to ASD-STE100. The goal is text that a
non-native-English engineer can read once and understand exactly.

- **One word, one meaning.** Use each technical term with one meaning
  and use the same term for the same thing everywhere ("mesh" stays
  "mesh" - not "grid" on page 2 and "discretization" on page 3).
- **Active voice, simple tenses.** "The solver converged in 400
  iterations", not "convergence was achieved". Past, present, or future
  simple only; avoid -ing verb forms where a simple tense works.
- **Short sentences.** Maximum ~20 words for instructions, ~25 for
  descriptive text. One idea (or one instruction) per sentence.
- **Short paragraphs.** Maximum 6 sentences; one topic per paragraph.
- **Keep the articles.** Write "the mesh", "a boundary layer" - do not
  drop "the"/"a" telegraph-style.
- **Instructions are commands.** "Run the script with --angqbf 180",
  not "the script should be run".
- **Break up noun clusters.** More than 3 nouns in a row ("boundary
  layer growth rate parameter study") - rewrite with prepositions
  ("study of the growth-rate parameter for the boundary layer").
- **Use vertical lists** for anything with more than two parallel items
  or steps.
- **State warnings and limitations directly and first**, in their own
  sentences - not buried in a subordinate clause.
- Plain words over formal ones: "use" not "utilize", "start" not
  "initiate", "show" not "demonstrate/illustrate", "about" not
  "approximately" (except in numeric tolerances where "approx." is
  conventional).

STE applies to body prose, captions, and the abstract. It does not
override correct technical names, standard symbols, or the exact
commands/units - those stay verbatim.

## Style rules

- No emojis. No em dashes - use hyphens, double hyphens, or colons.
- Every number in the abstract must appear again (with context) in a
  table or section body.
- Units everywhere; state the unit system once ("all meters") if uniform.
- Tables: short enumerable facts only; explanation goes in prose.
- Use `uv run --with <pkg>` for all Python (reportlab, pillow, pyvista,
  numpy, matplotlib, pypdfium2) - no global installs.
- Temp/intermediate files (probe renders, .geo scripts, crops) go in the
  session scratchpad; only the PDF and final figure PNGs go in the
  project tree.

## Scripts

- `scripts/report_style.py` - import into your make_report.py: page
  styles, table style, `fig_single`, `fig_pair` helpers, doc factory.
- `scripts/crop_pairs.py` - union-content-bbox cropping for image pairs
  and singles (edit the PAIRS/SINGLES lists at top, or import
  `crop_pair`/`crop_single`).
- `scripts/verify_pdf.py` - `uv run --with pypdfium2 --with pillow
  python verify_pdf.py report.pdf outdir/` renders each page to PNG for
  inspection.

## Failure modes to avoid

- A figure nobody probed (wrong camera, washed-out color range, subject
  off-frame) - always Read probe images back before finalizing.
- Comparison pairs with different zoom/crop - meaningless.
- Color range covering the whole data span when the structure of
  interest lives in 5% of it - measure the interesting range first,
  then set clim to it.
- Restating the figure in its caption ("pressure field around body")
  instead of saying what it demonstrates ("stagnation front wraps the
  tip symmetrically; blockiness is the P=1 representation").
- Writing the report before the numbers exist, then backfilling - the
  narrative should be derived from measured results, not vice versa.
